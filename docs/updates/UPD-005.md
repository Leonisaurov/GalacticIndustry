## 1. Resumen

Convertir el panel de continuidad en un seguimiento por versiones. La
implementación inicial pasa a ser la versión `0.1` y cada actualización
`UPD-XXX` recibe una etiqueta visual estable (`0.2`, `0.3`, …). El panel
mantiene una sola página `docs/dashboard/index.html` y una única plantilla
dinámica: un selector horizontal, una línea de tiempo y un contenido que cambia
según la versión seleccionada.

## 2. Motivación

El panel actual presenta el plan maestro como bloque principal y apila todas las
actualizaciones en una página continua. A medida que se añaden versiones, la
lectura se vuelve larga y es difícil responder rápido a: qué versión está
seleccionada, qué objetivo tiene, cuánto progreso lleva y qué queda pendiente.
El tracker ya contiene los datos necesarios; falta una representación por
versiones sin duplicar HTML ni crear una página por actualización.

## 3. Alcance

**Incluye:**

- Selector horizontal de versiones, de la más reciente a la más antigua.
- Dos modos: compacto (por defecto) y descriptivo, con preferencia local.
- Línea de tiempo horizontal, de `0.1` a la versión más reciente, con puntos
  seleccionables que comparten el estado del selector.
- Plantilla única de contenido: identificación, progreso, grupos/etapas, tareas,
  historial y pendientes de la versión seleccionada.
- Progreso calculado solo con las tareas de la versión seleccionada.
- Etapas originales solo para la versión `0.1`; las actualizaciones sin grupos
  propios muestran una lista plana de tareas.
- Sección global independiente: resumen, estado actual, actualizaciones
  pendientes de aprobación, decisiones, problemas, tareas bloqueadas ajenas a la
  versión seleccionada y sesiones recientes.
- Metadatos mínimos y estables: `displayVersion`, `objective` y
  `meta.initialVersion`; los IDs internos no cambian.
- Validación de versiones, objetivos y grupos opcionales en
  `tools/sync-dashboard.py`.
- Pruebas de datos y de renderizado del panel.

**No incluye:**

- Crear un HTML por actualización.
- Duplicar plantillas, CSS o JavaScript por versión.
- Cambiar IDs de actualizaciones, tareas o sesiones.
- Reabrir o reescribir etapas y tareas históricas.
- Cambiar el código del videojuego.
- Introducir servidores, backend, bases de datos, CDN, APIs o frameworks.
- Convertir los borradores de `localStorage` en fuente de verdad.

## 4. Modelo de datos

El tracker sigue siendo la fuente canónica. Se añaden únicamente metadatos de
presentación:

```json
"meta": {
  "initialVersion": {
    "id": "BASE",
    "displayVersion": "0.1",
    "name": "Implementación inicial",
    "description": "…",
    "objective": "…",
    "date": "2026-11-07"
  }
}
```

Cada actualización conserva su `id` y añade:

```json
"displayVersion": "0.2",
"objective": "Objetivo principal de la actualización.",
"groups": []
```

`displayVersion` es una etiqueta visual estable. No sustituye al `id` ni se usa
para calcular el estado. `groups` es opcional: si existe, el panel lo muestra
como grupos de trabajo; si no existe, no inventa etapas. La versión inicial se
construye con `stages` y `tasks`; las actualizaciones con `updates[].tasks`.

Regla de progreso: se cuentan solo las tareas `category=implementation` con
`countsForProgress=true`. El porcentaje es `completadas / total` de esa lista.
Si la lista está vacía, el panel muestra `—` y no inventa un porcentaje. Las
versiones `RECHAZADA` o `ARCHIVADA` no contabilizan tareas pendientes.

## 6. Criterios de aceptación

1. La implementación inicial aparece como versión `0.1`.
2. `UPD-001` aparece como `0.2`, `UPD-002` como `0.3`, `UPD-003` como `0.4`,
   `UPD-004` como `0.5` y `UPD-005` como `0.6`.
3. Al abrir el panel se selecciona la versión correspondiente a
   `meta.currentUpdateId`; si no existe, la actualización activa más reciente; si
   no hay activas, la más reciente registrada, mostrando su estado real.
4. Una propuesta pendiente de aprobación se muestra con su estado y sin
   presentarse como trabajo en desarrollo.
5. El modo compacto es el predeterminado; el descriptivo muestra número,
   identificador, nombre, descripción, objetivo, estado y progreso.
6. El selector y la línea de tiempo comparten la misma selección.
7. Seleccionar una versión cambia la cabecera, el progreso, los grupos, las
   tareas, el historial y los pendientes mostrados.
8. El progreso usa solo tareas de la versión seleccionada.
9. Las etapas `S0`…`S11` solo aparecen en la versión `0.1`.
10. Las actualizaciones sin `groups` no muestran etapas inventadas.
11. Los pendientes globales no se mezclan con los de la versión seleccionada.
12. Las versiones históricas conservan sus datos y etiquetas.
13. Añadir una actualización nueva la muestra con la misma plantilla.
14. No se generan páginas HTML independientes por actualización.
15. La búsqueda y los filtros de tareas siguen funcionando.
16. El panel funciona mediante `file://` sin red.

## 7. Riesgos y limitaciones

- El panel es una aplicación JavaScript sin framework; el renderizado se prueba
  con un DOM mínimo en Node, no con un navegador real en cada ejecución.
- `localStorage` puede estar restringido en algunos contextos `file://`; el modo
  compacto sigue siendo el valor de respaldo.
- Las actualizaciones antiguas no tienen `groups`; se muestran como listas
  planas, que es el comportamiento correcto y no una carencia.
- La versión inicial conserva sus 93 tareas y 12 etapas; su historial puede ser
  largo, por lo que se limita a las sesiones más recientes con opción de
  expandir.
- No se modifican datos históricos salvo metadatos de presentación
  (`displayVersion`, `objective`).
